## Context

[ADR-0012](../../INV-43987%20-%20Bulk%20Anchoring/decisions/ADR-0012%20Durable%20Workflows%20Engine.md) named `@nestjs/workflows` as the long-term durable-orchestration engine, gated on a NestJS/cqrs upgrade. This ADR is the diary of that upgrade: analysis, step log, and the final verdict on how much the current implementation breaks.

Scope by request: tick NestJS up **only in the microservices that are currently running**, starting with `inv-hub-ms` (`hub-service`). The human will shut the other services down so we can experiment on `hub-service` in isolation. `@inveniam/nest-aws-cqrs` is updated **after** the core libs (expected to break first; fixed in a later diary entry).

### TypeScript worry — mostly already handled

`hub-service` already compiles on its own nested **TypeScript 5.9.3** (`apps/hub-service/node_modules`), even though the rest of the workspace hoists `4.7.3` (every `shared-modules/*` dev-pins `4.7.3`). NestJS 12 needs TS ≥ 5.x, so for `hub-service` the compiler is already modern. The TS risk is concentrated in the shared-modules if/when they need to recompile against the new Nest types.

### Why "only hub-service" is not isolated by default

1. **shared-modules declare Nest as hard `dependencies`, not `peerDependencies`.** `@inveniam/logger`, `@inveniam/events`, `@inveniam/nest-aws-cqrs`, `@inveniam/exception-handling`, etc. pin `"@nestjs/common": "8.4.7"` (and `core`/`cqrs`/`typeorm`) in `dependencies` with exact versions. Today Yarn hoists a single copy.
2. If only `hub-service` goes to 12, Yarn installs **two** copies of `@nestjs/*` (8.4.7 for shared-modules, 12.x for the app). NestJS cannot run with two `@nestjs/common` instances in one process — DI tokens and `reflect-metadata`/`instanceof` checks require a single module instance → runtime failure.
3. `hub-service` consumes shared-modules by **TS path alias** (compiles their source, not built `dist`), so their decorators (`@Injectable`, `CqrsModule`) must compile against the same Nest version as the app.

→ To move `hub-service` we must also move the Nest deps of the shared-modules it imports. Mitigation chosen for the experiment: the human shuts the other services down, so we can bump the shared Nest line workspace-wide and only exercise `hub-service` at runtime.

### Hardest blocker — `@inveniam/nest-aws-cqrs`

The custom SNS→SQS event bus (core of hub-service eventing) reaches into **cqrs internals** that were refactored/removed across cqrs 9→10→11→12:

- `@nestjs/cqrs/dist/services/explorer.service` (`ExplorerService`)
- `@nestjs/cqrs/dist/decorators/constants` (`EVENTS_HANDLER_METADATA`)
- `@nestjs/cqrs/dist/helpers/default-pubsub` (`DefaultPubSub` — removed in newer cqrs)
- `InvalidSagaException`, `ObservableBus` semantics

This will not compile/run on cqrs 12 without a rewrite. Per the plan it is fixed **after** the core bump.

### Other breaking changes 8 → 12

- `platform-express` 12 defaults to **Express 5** (new `path-to-regexp`, routing edge cases, wildcard `*` → named params).
- Node 20+ runtime.
- `reflect-metadata` 0.2.
- Majors for `@nestjs/config` (4→12 numbering), `typeorm`, `passport`, `swagger`, `jwt`, `terminus`, `mongoose`, plus `@types/*`.
- `@nestjs/cqrs` saga/handler API changes beyond the internal-import problem.

## Decision

Proceed with the upgrade to NestJS 12 on the running services, `hub-service` first:

1. Bump the Nest core libs + peers in `hub-service` (and the shared Nest line it depends on) to 12.x, `reflect-metadata` to 0.2.
2. Leave `@inveniam/nest-aws-cqrs` broken on purpose; fix it in a later entry.
3. Experiment only on `hub-service` (other services off).
4. Record every step and the final breakage assessment here.

## Alternatives considered

- **peerDependencies conversion** — convert shared-modules Nest deps to wide-range `peerDependencies` so no shared-module dictates a version. Cleaner long-term, more upfront churn; initially deferred, **adopted 2026-11-17** (see Diary).
- **Spike in a throwaway worktree** — safer, but the human prefers to experiment directly on `hub-service` with other services off.
- **Stop at analysis** — rejected; the upgrade unblocks ADR-0012/0013.

## Consequences

- **Positive**: unblocks `@nestjs/workflows` (ADR-0012/0013); modernises the platform.
- **Negative / trade-offs**: `nest-aws-cqrs` rewrite required; Express 5 migration risk; whole shared Nest line moves even though only `hub-service` is exercised.
- **Follow-ups**: boot-verify the peerDependencies refactor (dev images bake `node_modules` → needs an image rebuild) and commit it; give `@inveniam/nest-aws-cqrs/cqrs-explorer` a real `exports`/built entry so the release Docker build resolves the subpath (today only the tsconfig alias covers it); address the pre-existing `YN0060` version mismatches as separate tech-debt (notably `mongoose 6.13.10` vs `@nestjs/mongoose@12`); make the data-room view-model replay actually fire (the `FIXME(nest12-upgrade)` sites) in its own tested change; **bump `typescript` to `5.9.3` in all affected `apps/*/package.json`** (only `shared-modules` were bumped — apps still pin `4.7.3`/`4.9.5`), which currently **blocks every production image build** because the isolated per-service `tsc` cannot parse the Nest 12 `.d.ts` (terminus); fix the `hub` `@zerodev/permissions` `TS2352`; re-confirm the transient `@nestjs/terminus@12.2.0` focus-install `quarantined` on `dataio`/`workflows`; **align the event-store data source naming across services** (legacy default-coupled `EventStoreModule` vs the `next` named connection) so the `DataSourceNameRegistry` warning can be removed without breaking DI — see Open questions.

## Open questions

- **Event-store data source naming is inconsistent across services, and the inconsistency is load-bearing.** Two event-store implementations coexist with opposite TypeORM connection assumptions:
  - The **legacy** `@inveniam/event-store` `EventStoreModule` (`event-store.module.ts`: `TypeOrmModule.forFeature([EventData])` + `EventDataRepository` injecting the **unnamed/default** `DataSource`) requires the event-store connection to be the **default** data source.
  - The **`next`** path (`event-store/src/next`) uses an **explicitly named** connection (`@InjectDataSource(CONNECTION_NAME)`), leaving the app's main DB free to be the default.

  Consequence: on services running the `next` path (e.g. `hub`) the event-store classic `forRootAsync` (`NEXT.DatabaseModule`) and the app's main DB both register under the **default** name at the `forRootAsync` options level (the ES name is set only inside the factory result), so Nest 12's eager `DataSourceNameRegistry` logs `A data source with the default name is already registered`. The warning is **benign there** (both data sources still initialise; the app boots). But it is **not** safe to silence by naming `NEXT.DatabaseModule` at the options level: doing so moves that provider off the default token, which **breaks every legacy-path service** whose `EventDataRepository` injects the default `DataSource` (confirmed: `iam` fails boot with `UnknownDependenciesException` on `EventDataRepository`).

  **Decision needed:** unify all services on the `next` **named-connection** event-store (`@InjectDataSource(CONNECTION_NAME)` + `forFeature(..., CONNECTION_NAME)`), retiring the legacy default-coupled `EventStoreModule`, so (a) the main app DB owns the default connection cleanly, (b) the event-store connection is consistently named, and (c) the `DataSourceNameRegistry` warning disappears without breaking DI. Until that alignment lands, the warning **stays** (load-bearing for the legacy path) and is accepted as benign.

Fix (canonical peer+dev library pattern): each of the **29** shared-modules with framework peers now **mirrors its own peer subset into `devDependencies`** at the concrete 12.x versions the apps pin (`@nestjs/common` 12.5.1, `core` 12.5.1, `config` 12.1.1, `cqrs` 12.1.3, `schedule` 12.0.4, `typeorm` 12.0.3, `axios` 12.0.2, `swagger` 12.1.2, `terminus` 12.2.0, `jwt` 12.0.5, `passport` 12.0.2, `mapped-types` 12.0.1, `mongoose` 12.0.1, `platform-express` 12.5.1, `rxjs` 7.8.1, `reflect-metadata` 0.2.2). `peerDependencies` are untouched, so consuming services still own the runtime version (devDeps never install transitively into consumers). The 5 Nest-free modules (`SharedInterfaces`, `Events`, `EnvChecker`, `AWS`, `SharedUIComponents`) are left alone. The `YN0002` intra-workspace peer noise returns (accepted as benign), but the build-breaking `TS2307` is gone. Verified by a clean `shared-modules` image rebuild. Uncommitted.
- **2026-11-17 — `DataSourceNameRegistry` warning: attempted an options-level name, reverted (regressed `iam`).** Runtime-verifying the peer refactor on `hub` surfaced a WARN `A data source with the default name is already registered` from `@nestjs/typeorm` 12's new eager `DataSourceNameRegistry` — `hub` runs event-store **classic** mode (`ENABLE_EVENTSTORE=true`), so `NestAwsCqrsModule.forRoot` pulls `NEXT.DatabaseModule` (`event-store/src/next/event-store.database.ts`, `TypeOrmModule.forRootAsync`), and both it and the app's main `invhub` DB register under the **default** name at the `forRootAsync` options level (the ES name is set only inside the factory result). `hub` booted fine regardless (`Nest application successfully started`, both data sources initialised). To silence it I added `name: CONSTANTS.CONNECTION_NAME` at the `forRootAsync` options level → `hub` went clean. **But it broke `iam`:** `UnknownDependenciesException` for `EventDataRepository`'s `DataSource` — `iam` runs the **legacy** `EventStoreModule`, whose `EventDataRepository` injects the **unnamed/default** `DataSource` that was being supplied by that very (previously-unnamed) `NEXT.DatabaseModule`. Naming it moved the provider off the default token, so the legacy injection could no longer resolve. **Reverted** `event-store.database.ts` (net-zero); the warning returns on `hub` but every service boots. Verified in Graylog: pre-revert `iam` threw `UnknownDependenciesException` and never started; `hub` clean with the warning present. Root cause is the cross-service inconsistency recorded in **Open questions** — the warning cannot be removed until the event-store data source naming is aligned app-wide.

- **2026-11-18 — Production image build check across every affected service: no service image builds; the per-service `typescript` pin was never bumped.** Built the production (`*-ms-prod`) image for each affected microservice (the `shared-modules:latest` + `ms-prod:latest` bases build fine). **All 15 affected services FAIL**, in three shapes:
  - **12 services** (`iam`, `relay`, `deals`, `tasks`, `data-room`, `metachain`, `scheduler`, `organisations`, `notifications`, `websockets`, `automated-workflow`, `batch-processing`) fail in the `*-ms-built` stage at `npm run build` → raw `tsc -p tsconfig.build.json`, on a **parse cascade** inside `@nestjs/terminus@12.2.0/dist/health-check/health-check-executor.service.d.ts(24,…)`: `TS1139`/`TS1434`/`TS1068`/`TS1005`.
  - **`dataio` + `workflows`** fail one step earlier, at `yarn workspaces focus --production`, with `@nestjs/terminus@npm:12.2.0 … quarantined` (a resolution/fetch failure, likely a transient npm quarantine); they would hit the same TS wall right after.
  - **`hub`** (already on TS `5.9.3`) parses terminus cleanly and fails only on a **genuine** `@zerodev/permissions/policies/callPolicyUtils.ts(120,39)` `TS2352` (deeply nested `readonly` array → `ByteArray` conversion) — a separate real error that persists regardless of the TS bump.
  - **Root cause — the apps were never bumped.** The earlier "bump to 5.9.3" step covered `shared-modules/*` only; `apps/*/package.json` still pin `typescript` `4.7.3` (`scheduler` `4.9.5`), and only `hub-service` is `5.9.3`. The production path compiles each service **in isolation** — the `*-ms-built` stage runs the service's **own** pinned `tsc` — and TS 4.7/4.9 cannot even **parse** the TS-5-era `.d.ts` files the NestJS 12 ecosystem ships (terminus). The split is the proof: `hub` on 5.9.3 clears terminus and only trips on `@zerodev`; everything on 4.7.x/4.9.x chokes on the parser.
  - **`skipLibCheck: true` does not rescue it** (it is set in the root `tsconfig.build.json`): `TS1139`/`TS1434`/`TS1005` are **grammar/parse** errors, not semantic lib checks, so they surface anyway.
  - **Why dev was green and hid this:** the `*-ms-dev` target runs `nest start` (transpile-only) inside the full monorepo, where the root hoists a modern TS, so dev boots — Graylog showed all 10 services `Nest application successfully started`. The isolated release `tsc` is the only path that resolves the stale per-service `4.7.3`.
  - **Verdict: no production image builds in the current state.** Prereqs: (1) bump `typescript` `4.7.3`/`4.9.5` → `5.9.3` across all affected `apps/*/package.json` (match `hub`) and refresh `yarn.lock`; (2) re-run `dataio`/`workflows` to confirm the terminus `quarantined` focus-install was transient; (3) fix the `hub` `@zerodev/permissions` `TS2352` as its own change. **No code changed during this check** (build check only); logs in `/tmp/prodbuild-logs/`.
