# Provisioning Review Findings

**Summary**: Punch list from the code review of `INV-42559-measurabl-anchoring` vs `develop` (204 files, ~11k lines; 49 provisioning suites / 187 tests green). Chain structure, the `deal_anchors` SQL, and the register chain-hash fix are sound. High findings R2–R4 are **done** (org-scoped advisory locks + a funding budget that fits the queue's handler timeout). Medium findings R5–R12 are **done**: estimates now carry `bigint` wei with per-write Hub buffers, EIP-1559 price headroom, a re-quote after the poll, a probe that no longer swallows transport errors, failed balance reads abort instead of over-funding, `tx.wait` timeout is "not yet confirmed", Hub write receipts are checked against the identity, and gas logs keep `walletId` / `from`. What is left is R13 (provider reuse, Low) and R14 — Hub's `estimate()` still drops the identity wallet its own controller already resolved, which would retire the ethers quote path (and R13) if fixed. R1 was **rejected** — Hub stores no seed. Each finding is numbered so it can be closed one at a time.

**Sources**: Branch `INV-42559-measurabl-anchoring` in `~/work/inveniam/inveniam.io`; Hub `apps/backend/src/wallets/` in `~/work/inveniam/hub`; [Hub Onboarding Chain](Hub%20Onboarding%20Chain.md); [Identity Wallet Signing](Identity%20Wallet%20Signing.md); [Open Questions](INV-42559%20-%20Measurabl%20provision/wiki/Open%20Questions.md) #8, #9, #10, #12.

**Last updated**: 2026-09-29

## R1 — Org mnemonic reaches Hub — rejected 2026-09-29

**Original claim**: `EnsureHubWalletStep` mints the org mnemonic through Hub (`POST /wallets/keys/generate`) and `EnsureHubIdentityWalletStep` posts it back to `POST /wallets/keys/derive` for every portfolio leaf, so Hub holds the seed that controls every portfolio wallet — contradicting [Open Questions](INV-42559%20-%20Measurabl%20provision/wiki/Open%20Questions.md) #9 and #10.

**Rejected.** Hub is stateless with respect to the mnemonic, by design (source: `hub/apps/backend/src/wallets/wallets.service.ts`):

- `generateWalletKeys` returns `generateMnemonic(strength)` from `bip39` and persists nothing.
- `deriveKeysFromMnemonic` normalizes, `validateMnemonic`s, derives in memory through `mnemonicToSeed`, and returns `{ privateKey, address }`.
- Hub stores only the derived key pair in its own vault. It has no mnemonic storage and no permission to hold one; the phrase is handed to the user as a file.
- No request-body logging interceptor in the backend, so the phrase is not captured in transit logs either.

[Open Questions](INV-42559%20-%20Measurabl%20provision/wiki/Open%20Questions.md) #9 ("Hub gets leaf keys only") and #10 are therefore accurate as written — they describe storage, and Hub stores no seed.

What remains is transit only: the phrase crosses the wire to a first-party service over TLS on each identity provision. IO could derive locally with ethers (`HDNodeWallet.fromPhrase`, already used in `NvnmNativeTransfer`) and drop the `/wallets/keys/derive` round trip. That is a **simplification** — one fewer Hub call on the provisioning hot path, one fewer failure mode — not a security fix, and it is not tracked as a finding here.

## R2 — Parent EOA nonce collisions

Every top-up signs from `m/44'/60'/0'/0/0` through a signer built fresh per call, with no nonce management (`.../chain/shared/nvnm-native-transfer.ts`). Two `ClientDLTTransaction` events for the same organisation — different portfolios, or a redelivery — read the same pending nonce, and one transfer dies with `nonce too low` or `replacement underpriced`.

**Fixed 2026-09-29.** New `OrganisationProvisioningLock` (`organisation-provisioning/infrastructure/organisation-provisioning.lock.ts`) takes a session-scoped `pg_try_advisory_lock(scope, hashtext(orgId))` on a dedicated `QueryRunner`, so acquire and release land on the same connection. `IdentityWalletTopUp.transferFromParent` now runs the leftover re-read **and** the send inside `OrganisationLockScope.ParentWalletNonce` — a waiting run re-reads the balance under the lock and returns `false` instead of signing a second transfer on the same nonce. Bounded wait (150s) then `UnprocessableEntityException`, so a stuck holder cannot pin a consumer indefinitely. Same lock service, different scope, serves R3.

## R3 — HD leaf index race

`EnsureHubIdentityWalletStep` reads `mapping.identityWalletIndex`, derives, POSTs the wallet, and only then calls `nextIdentityWalletIndex`. Two concurrent portfolio provisions for one organisation read the same counter and derive the **same leaf**: two Hub identities share an address and a private key, and funding one silently pays for the other.

**Leaves must stay dense.** Reserving the leaf up front fixes the race but burns a leaf on every failed create. That was tried before and removed on purpose: reconstruction was never designed (correct behaviour is still unknown), so the property worth preserving is that N portfolios occupy leaves `1..N` on the shortest path — nobody should have to guess how far to walk the derivation path to find all N sub-wallets. Gaps break that.

**Fixed 2026-09-29 — keep read-then-increment, serialise it.** The counter still ticks only after a successful create, so no failure leaves a hole. `EnsureHubIdentityWalletStep.process` now runs the whole existence-check → read counter → derive → create → tick sequence inside `OrganisationLockScope.IdentityHdLeaf`, which is what makes the read-modify-write safe. Cost: portfolio provisioning serialises per organisation across a handful of Hub calls. The critical section holds no chain waits, unlike the funding lock.

Two scopes, never one: `IdentityHdLeaf` (42560) and `ParentWalletNonce` (42559) guard different resources and run on different connections, so sharing a key would self-deadlock if the sections ever nested.

## R4 — Funding budget exceeds `handleMessageTimeout`

Measured against the real queue config rather than guessed:

| Setting | Value | Source |
| ------- | ----- | ------ |
| `visibilityTimeout` | 240s deployed (10s default) | `helm/configs/ns.yaml`, `apps/hub-service/src/config/environment.ts` |
| `heartbeatInterval` | 9s | same |
| `handleMessageTimeout` | **180s** | same |
| `NVNM_NATIVE_TRANSFER_TIMEOUT_MS` | 120s | `nvnm-native-transfer.ts` |
| `IDENTITY_FUNDS_POLL_DEADLINE_MS` | 180s | `identity-wallet-funds-poll.ts` |

Visibility expiry is **not** the problem: `SqsConsumer` passes `heartbeatInterval` to `sqs-consumer`, which extends the message while the handler runs. The problem is `handleMessageTimeout` — `sqs-consumer` aborts the handler at 180s, while the funding worst case is 120 + 180 = **300s**. The message is then not deleted, so it is redelivered and starts a second chain.

R2 removes the damage: the duplicate now serialises on the org lock, re-reads leftover, finds the wallet funded, and no-ops. What remains is wasted work and a confusing `Failed` log for a chain that was actually fine.

**Fixed 2026-09-29 — shrink the budget.** Chosen over raising `HANDLE_MESSAGE_TIMEOUT` (a stuck handler would hold a consumer slot longer) and over a resumable funding step (correct, but a much larger change for a path that R2 already makes safe). `NVNM_NATIVE_TRANSFER_TIMEOUT_MS` 120s → **60s**, `IDENTITY_FUNDS_POLL_DEADLINE_MS` 180s → **90s**: worst case 150s, 30s of margin for the rest of the chain.

Only one funding step can run per message, so the budget is not doubled: `EnsureRegistryFundsStep` skips funding when `deal_anchors.registry` already exists — the only path that chains synchronously into the document chain — and when it does fund, `CompleteRegistryProvisioningStep` parks for the register webhook instead of continuing. `CommandBus` is the in-process `@nestjs/cqrs` one, so that distinction is what keeps the two funding steps apart.

`IDENTITY_FUNDS_BUDGET_CEILING_MS` records the 180s ceiling and a unit test asserts `transfer + poll` stays under it with ≥30s margin, so raising either timeout fails the build rather than production.

## R5 — Money through JS `number`

`addRecordGasToEstimate` turns `bigint` wei into `Number(formatEther(...))`, `Number(gas)`, `Number(gasPrice)` (`.../chain/shared/nvnm-add-record-gas.ts`), and `identity-wallet-top-up-value.ts` converts back with `getBigInt(gasPrice)` and `parseEther(String(balance))`. `getBigInt` throws on a non-integer, so a gas price above 2⁵³ wei or any float artifact hard-fails the chain instead of degrading.

**Fix**: carry `bigint` wei on `IdentityWalletTopUpEstimate`; format only for logs.

**Fixed 2026-09-29.** `IdentityWalletTopUpEstimate` is now `{ feeWei, gas, gasPrice, requiredWei }` as `bigint`. Hub ETH numbers convert at the I/O boundary via `ethNumberToWei`; logs get strings from `topUpEstimateLog` so `JSON.stringify` cannot throw on bigint.

## R6 — No gas-price headroom

`estimateCalldata` reads `feeData.gasPrice` — the legacy field — at quote time, and nothing re-quotes after a poll that can run three minutes. The 6× in `hubBufferedGas` is headroom on gas *units*, not price. If Hub signs a type-2 transaction reserving `maxFeePerGas`, or base fee moves during the poll, the wallet is short — the same `insufficient funds` outcome that killed [Open Questions](INV-42559%20-%20Measurabl%20provision/wiki/Open%20Questions.md) #12 Variant D.

**Fix**: use `max(gasPrice, maxFeePerGas)`, add a configurable price multiplier, and re-check the requirement after the poll before handing off to the write step.

**Fixed 2026-09-29.** `quoteGasPrice` takes `max(gasPrice, maxFeePerGas)` and applies `nvnm.gasPriceHeadroomPercent` (default 120, env `NVNM_GAS_PRICE_HEADROOM_PERCENT`). After the leftover poll, `ensureQuoted` re-runs the ethers quote; if leftover no longer covers, the step throws and the chain retries rather than writing short.

## R7 — Buffer applied to the sum

`combineTopUpEstimates` adds the `addRegistry` and `addRecord` gas, then `hubBufferedGas` buffers the total. `max(g*2, g+30000)` is not additive, so this only equals the sum of per-write buffers while both writes exceed 30k gas. Today they do (≈55k and ≈166k), so the number is right — it becomes a silent underfund the moment a write lands below that.

**Fix**: buffer each write, then sum.

**Fixed 2026-09-29.** `combineTopUpEstimates` calls `hubBufferedGas` on each write, then sums `requiredWei`. A sub-30k write can no longer silently underfund the combined leftover check.

## R8 — The `addRecord` probe

`estimateRegisterThenDocument` walks up to `ADD_RECORD_QUOTE_REGISTRY_LIMIT` (10) recent on-chain registries, calling `eth_estimateGas` against each until one does not revert. Every failure is swallowed by a bare `catch {}`, so a dead RPC, a stale ABI, and a permissions change all look identical and quietly degrade to `ADD_RECORD_EOA_GAS_STAND_IN = 166_014n` — one live measurement frozen into a constant.

**Fix**: separate revert from transport error; move the stand-in to config with a metric or alarm when it is used; cache the probe per organisation, since it does not vary by deal.

**Fixed 2026-09-29.** Reverts (`CALL_EXCEPTION` / `NvnmEstimateRevertError`) try the next registry; any other error fails the quote. Stand-in gas comes from `nvnm.addRecordEoaGasStandIn` (env `NVNM_ADD_RECORD_EOA_GAS_STAND_IN`, default `166014`) and logs `addRecordStandInUsed: true` as a `warn`. A successful live probe is cached per organisation so later deals skip the walk; stand-in is not cached.

## R9 — Swallowed balance reads over-fund

`HubLedgerQuotes.readIdentityWallet` logs and drops a balance error; `IdentityWalletTopUp.readLeftover` does the same and returns `undefined`, which `identityWalletTopUpWei` reads as a zero balance and funds the **full** buffer. A transient Hub 5xx becomes a real on-chain transfer.

**Fix**: fail the step. The chain is retried anyway, and retrying is cheaper than paying twice.

**Fixed 2026-09-29.** `HubLedgerQuotes.readIdentityWallet` and `IdentityWalletTopUp.readLeftover` rethrow a failed `GET /ledgers/balance/{walletId}`. A Hub 5xx no longer looks like a zero leftover.

## R10 — `tx.wait` timeout is not a failure

If the 120s wait elapses the step throws, but the transfer may still confirm. The retry re-reads leftover so it self-corrects, yet the log records a failure for a transfer that succeeded. `NvnmNativeTransfer.send` returns the tx hash and `IdentityWalletTopUp` discards it.

**Fix**: log the hash, and distinguish "not yet confirmed" from "rejected".

**Fixed 2026-09-29.** Ethers `TIMEOUT` on `tx.wait` is "not yet confirmed": the hash is logged and returned so the leftover poll can pick the transfer up. Any other wait error is rejected and thrown. `IdentityWalletTopUp` logs the hash on send.

## R11 — No proof Hub signed as the identity

Per [Identity Wallet Signing](Identity%20Wallet%20Signing.md), Hub silently falls back to the org wallet when the identity, the email, or its NVNM wallet do not line up. In that case the whole top-up was wasted and the organisation paid, with nothing in the logs saying so.

**Fix**: compare the receipt `from` against `context.walletAddress` on completion; log or alert on mismatch.

**Fixed 2026-09-29.** New `IdentityWriteSigner` fetches the receipt for the succeed-event tx hash and compares `from` to the identity address from `get-wallet-info` (or the deal's Measurabl email). Mismatch is a `warn` with both addresses — it does not fail the chain. Wired from `StoreDealAnchorRegistryCommand` (register) and `LogDocumentSyncFinishedSaga` (addRecord).

## R12 — Redaction hides the gas debugging keys

`SECRET_LOG_KEYS` in `apps/hub-service/src/config/client-provisioning.log.ts` strips `walletId`, `walletAddress`, and `from` — exactly what the gas log sites pass (`identity-wallet-funds.ts`, `nvnm-add-record-gas.ts`). The fields are computed and silently dropped, so a funding failure cannot be tied to a wallet. The rules also disagree with each other: `sanitizeClientProvisioningPath` masks `/wallet/{id}` but not `/ledgers/balance/{walletId}`, so the id leaks through the path anyway.

**Fix**: keep `walletId` and `from` (a Hub UUID and a public address are not secrets), drop the now-dead log args elsewhere, and make the two path rules agree.

**Fixed 2026-09-29.** `SECRET_LOG_KEYS` no longer strips `walletId`, `hubWalletId`, `walletAddress`, or `from`. `sanitizeClientProvisioningPath` no longer masks `/wallet/{id}`, so it agrees with `/ledgers/balance/{walletId}` — both keep the id.

## R13 — Provider per call

`estimateCalldata` and `listRecentRegistryIds` each construct a `JsonRpcProvider` — up to three per quote — with no reuse and no `destroy()`, each repeating chain-id detection.

**Fix**: inject one provider or provider factory per network.

## R14 — Hub `estimate()` drops the identity wallet

This is [Open Questions](INV-42559%20-%20Measurabl%20provision/wiki/Open%20Questions.md) #12 Variant A, located. **Not implemented** — but the missing piece is smaller than #12 implies, and it is entirely inside Hub.

IO already sends `userEmail`: `EstimateTxCostPayloadDTO` carries it and the NVNM codec returns it alongside `tx`, so it reaches `POST /ledgers/estimate`.

Hub already resolves the identity wallet from it. In `hub/apps/backend/src/transactions-process/ledgers.controller.ts` (`estimateTransactionFee`), a present `userEmail` routes to `validateUserWallet(user, payload.userEmail)` and the resolved `userWallet` is passed into `EstimateTransactionFeeQuery`.

Hub then throws it away. `ProcessTransactionService.estimate` destructures `{ organization, orgWallet, txPayload, walletPassword, accessKey }` — no `userWallet` — and connects the provider with `orgWallet.keys.encoded` / `orgWallet.id`. A `userWallet` branch that decodes the identity keys and calls `prepareRelayerPayload` sits **commented out** immediately below `validatePayload`. So the estimate always runs `from` the master/org wallet, which is why `addRecord` on an identity-created registry comes back `unauthorized`.

`write` in the same service already does it right:

```ts
const isIndividual: boolean = !!userWallet?.keys?.encoded;
const wallet: WalletEntity = isIndividual ? userWallet : orgWallet;
```

**Fix (Hub)**: mirror that selection in `estimate` — read `userWallet` off the payload and connect the provider with `wallet.keys.encoded` / `wallet.id` — or re-enable the commented relayer-payload block. Estimate and write then agree on the signer, which is the invariant #12 needs. Still requires an explicit ask: Hub is outside the provisioning directory.

**Fix (IO, after Hub lands)**: retire the ethers quote path (R5–R8, R13 go with it) and move Register and Sync back onto `/ledgers/estimate`. Until then, `HubAdminClient.estimateTxCost` is dead code reached only from its own test, and the `FIXME`s in `NvnmAddRecordGas`, `IdentityWalletFunds`, and `EnsureDocumentFundsStep` should name this exact gap rather than "Hub estimate always quotes the org wallet".
