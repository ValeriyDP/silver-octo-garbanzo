# Anchoring Bucket Module

> [!warning] On hold
> This investigation is on hold. Nothing here is a candidate for implementation. Use it as reference only.

Switch this note to Excalidraw view in Obsidian, or open the standalone JSON on excalidraw.com. Module shape of the proposed bucket: data room → source adapters → core → `anchoring_bucket`, left to right. Companion page: [Anchoring Bucket](Anchoring%20Bucket.md). Other diagrams: [Anchoring Bucket Diagrams](Anchoring%20Bucket%20Diagrams.md). Standalone JSON: [Anchoring Bucket Module.excalidraw](Anchoring%20Bucket%20Module.excalidraw).

Anchoring bucket: module and sources ^title

Data room is unchanged. The entry event picks the source adapter. Each adapter gives the core three things: how to take in an event, how to start a row, and which events finish it.
The core knows only rows, the per-key lock, and the two transactions. It never sees events or commands. ^subtitle

apps/hub-service/src/anchoring-bucket ^ft-core

Intake transaction
1  pg_advisory_xact_lock(queue_key)
2  INSERT waiting
    ON CONFLICT (source, taxonomy_id)
    DO NOTHING
3  claim oldest waiting if no in_flight
4  COMMIT ^t-intake

Finish transaction
1  find in_flight row by match
2  pg_advisory_xact_lock(queue_key)
3  UPDATE to sync_success | sync_failed
    WHERE status = in_flight
4  claim oldest waiting
5  COMMIT ^t-finish

Per-key lock
pg_advisory_xact_lock
AdvisoryLockScope.AnchoringBucketQueue = 2001
Intake and finish take the same lock ^t-lock

After COMMIT
the claimed row is started through
its own source adapter.
No transaction is held while
THE HUB is called. ^t-dispatch

anchoring_bucket

id, source, queue_key,
taxonomy_id, status,
reason, received_at

unique (source, taxonomy_id)
unique (queue_key)
  where in_flight
index (queue_key,
  received_at, id)
  where waiting ^t-table
